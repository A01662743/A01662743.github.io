03

How I Use AI

AI is a tool not my replacement.

I use conversational LLMs as technical thinking partners. Before asking for help, I try to understand the system myself: its architecture, constraints, existing responsibilities, and what I think a possible solution could look like.

I then explain that context to the LLM, question its suggestions, compare different approaches, and verify that the reasoning actually fits my project.

I manually integrate the parts I decide to use and validate the result myself. This keeps me actively involved in the architecture and implementation instead of delegating every step of the development process.

CASE STUDY
01.

Fire Rescue — Event Queue System

THE PROBLEM

During an explosion, multiple visual effects could execute simultaneously. Although the underlying game logic was working, the visual progression became difficult to follow.

The existing architecture already separated the explosion logic from the Unity visualization layer, so the challenge was finding a way to sequence visual events without unnecessarily changing those responsibilities.

HOW AI HELPED

I described the existing architecture to an LLM, including the Explosion Manager, the Unity Visualizer, the event flow, and the behavior I wanted to achieve.

Instead of asking for a finished implementation, I used the conversation to explore how an event queue could fit into the existing architecture, discussing event representation, sequencing, dispatching, and responsibility boundaries.

ARCHITECTURE

→

→

→

WHAT I DID

I evaluated the approaches against the actual codebase, selected the event-command approach, and manually integrated the queue and dispatcher into the Unity visualization system.

RESULT

Visual effects could be executed sequentially, making complex explosion interactions easier to understand while preserving the existing separation between simulation logic and visualization.
